# RoleFox v0.1 产品需求文档

- 状态：Accepted Product Baseline
- 版本：v0.1
- 更新日期：2026-09-09
- 当前仓库阶段：M0 / pre-alpha

## 1. Executive Summary

RoleFox v0.1 要验证的不是“AI 能不能推荐岗位”，而是：

> 一位求职者能否把真实履历、求职目标和有限授权交给系统，让一个合格机会在无需日常点击的情况下持续推进，直到面试确认或出现真正需要本人决定的例外。

v0.1 只建设一条窄而完整的 Autopilot 通道：一个本地工作区、一个活跃求职计划、有限岗位入口、一个可控投递路径、邮箱沟通、一个日历，以及“产品内 Inbox + 默认邮件”的通知组合。合成环境必须完整运行到 `SCHEDULED`；真实环境根据平台可行性以 L2 受控动作为默认，满足严格门槛后才开放局部 L3。

## 2. 问题定义

### 用户问题

主动求职者需要反复完成浏览、判断、去重、修改材料、打招呼、投递、查看回复、跟进和约时间。很多动作没有回应，但仍持续消耗注意力。现有招聘平台的主界面鼓励用户不断返回和操作，没有替候选人承担完整的推进责任。

### 现有替代方案的缺口

- 岗位聚合只减少搜索入口，仍需要人工判断和投递。
- 简历工具只优化材料，不负责后续推进。
- 投递追踪工具记录状态，但不主动完成下一步。
- 无规则的批量投递提高数量，却可能降低匹配质量并增加账号风险。

### 产品机会

RoleFox 成为跨渠道的候选人侧执行层：把用户意图转成版本化策略，在事实、权限和风险边界内主动推进机会，正常动作静默完成，异常才打扰用户。

## 3. 目标用户

### v0.1 核心用户

正在主动寻找知识工作岗位的技术友好型个人求职者：

- 每周需要处理约 10–50 个潜在岗位；
- 已有较明确的岗位、地点、薪资和排除条件；
- 申请主要在线完成，招聘沟通可以进入邮箱；
- 愿意自托管或接受基础配置；
- 重视隐私、申请质量和控制权；
- 愿意先校准若干动作，再开启受限自动运行。

产品不以“产品经理”等具体职位写死核心模型。首批测试者可以集中于知识工作者，以降低渠道和材料差异。

### 后续用户

- 同时尝试多个方向的转岗者；
- 跨地区、远程和多语言求职者；
- 不会自托管、需要桌面安装包或托管服务的普通求职者；
- 在候选人明确授权下协作的职业教练或就业服务机构。

### v0.1 暂不服务

- 招聘方、猎头和人才库运营者；
- 主要依赖线下门店、电话或即时线下沟通的求职流程；
- 希望每日无差别投递数百岗位的用户；
- 要求系统自动谈判、接受 Offer、授权背调或作法律声明的用户。

## 4. Jobs to Be Done

### 主 JTBD

> 当我需要认真找工作、但无法每天花数小时刷岗位和推进申请时，我希望一次性告诉系统“我是谁、我要什么、哪些事它可以替我决定”，让合格机会持续推进到面试确认，而我只在规则例外和面试发生时介入。

### 支撑 JTBD

1. **把求职意图变成规则**：明确硬条件、偏好、质量阈值、投递节奏、回答范围和可约面时间。
2. **放心委托**：确认系统不会虚构经历、投错硬条件岗位、重复投递或越权承诺。
3. **让机会持续前进**：用户不看页面时，系统仍能等待、跟进、处理初聊并完成排期。
4. **在面试时快速接管**：用户收到完整上下文和准备包，不必重新翻找岗位与沟通记录。

## 5. 产品承诺与边界

### 产品承诺

> **设定目标，等面试通知。**

在明确支持的求职通道内，RoleFox 将经过校准的候选人事实和委托策略转化为无需日常点击即可持续推进的高质量申请，直到约成面试或遇到真正的规则例外。

### 用户只负责三件事

1. 提供并确认真实事实。
2. 设定目标和可撤销的委托边界。
3. 收到已确认面试后参加面试。

### 永远不自动完成

- 捏造或夸大候选人事实；
- 接受或拒绝 Offer；
- 薪酬谈判、竞业、背调授权和法律声明；
- CAPTCHA、访问控制或平台风控绕过；
- 未经策略授权或人工确认的外部动作。

## 6. v0.1 最小完整通道

| 环节 | v0.1 选择 | 收敛理由 |
| --- | --- | --- |
| 用户 | 单用户、本地工作区 | 先验证个人闭环 |
| 求职计划 | 每个 Workspace 最多一个 `CALIBRATING` 或 `ACTIVE` Campaign；历史 Campaign 可只读监听 | 降低策略冲突，同时接收迟到回复和面试变更 |
| 岗位与历史申请入口 | 合成数据、CSV/JSON、手动链接、历史 Application 导入/登记、一个合规真实只读源 | 先登记用户已投机会并与岗位关联，避免 RoleFox 对存量申请重复投递；BOSS 直聘 Connector 后续单独推进 |
| 材料 | 一份简历变体和一段招呼语/求职信 | 不做完整排版编辑器 |
| 投递 | Fake Connector 完整闭环；一个真实 L2 动作或稳定人工交接 | 不把版本押在平台写接口上 |
| 消息 | 邮箱中的有限意图 | 避免同时维护多种聊天协议 |
| 跟进 | 自动跟进默认关闭；开启后每个 Application 最多一次规则化跟进，冷却期可配置 | 先验证“已读不回”处理价值，不把“最多一次”误解成默认自动发送 |
| 日历 | 一个 Provider 账户、一个写入日历；可读取同账户多个日历的 busy 并集 | 保证排期可验证，跨账户聚合延期 |
| 通知 | 产品内 Inbox 为强制事实来源；邮件默认外部通知；Webhook 为可选适配器 | 不把外部投递成功等同于用户已经看到 |
| 自动化 | 合成环境完整 L3；真实环境默认 L2 | 先建立信任与证据 |

如果找不到合规、稳定的招聘平台写入路径，v0.1 可以把该投递步骤明确降级为 L2 材料导出、表单预填预览和深链接交接，不得宣称真实岗位投递 Autopilot 已完成。该降级不豁免真实邮箱与真实日历发布门：v0.1 仍必须用真实 Provider 账户完成投后邮件读取/受控回复、日历查询/对账及 calendar-first 约面闭环验收。

## 7. 功能需求

| ID | 能力 | v0.1 要求 | 验收结果 |
| --- | --- | --- | --- |
| F01 | 本地工作区 | 初始化、语言、时区、币种、通知设置、导出与删除 | 新用户无需改代码即可创建工作区 |
| F02 | 事实与证据 | 导入一份简历，拆分工作、项目、教育、技能事实；标记已确认、待确认、禁止外用 | 任何生成声明都能回溯 evidence ID |
| F03 | 求职计划 | 目标岗位、地点、工作方式、最低薪资、排除项、关键词、渠道与节奏 | 硬条件可以直接决定进入或退出 |
| F04 | 岗位与存量申请处理 | 导入、标准化、过期判断和来源保留；允许导入或手工登记 RoleFox 启用前的历史 Application，并关联现有/新建 JobPosting；同源按 connector + externalId/规范 URL 精确去重，跨源疑似重复只建立候选组并由用户消歧 | 历史已投机会不会被当成新机会再次投递；同一已确认机会在 Workspace 内最多一个活跃 Application |
| F05 | 匹配判断 | 硬过滤优先，随后分项评分；展示理由、风险和缺失信息 | 每个处理决定可解释、可复现 |
| F06 | 材料生成 | 针对岗位生成简历变体和沟通文本，展示差异与事实来源 | 无证据声明被拒绝进入外发计划 |
| F07 | 校准与委托 | Dry-run、L2 逐次确认、按能力 L3、策略版本、期限、白名单、默认/硬限额、撤销和急停 | 用户明确知道新增授权、门槛与仍会升级的例外 |
| F08 | 动作执行 | 不可变 ActionPlan、内容哈希、幂等键、授权来源、过期、审计与失败关闭 | 重放不会造成重复外部动作 |
| F09 | 消息与跟进 | 识别确认、补充信息、常规问题、面试邀请；自动跟进默认关闭，用户显式开启且通过对应授权门后，无回复才可按冷却期跟进一次 | 未收到新消息时不要求用户反复检查，且首次配置不会隐式开启外发 |
| F10 | 初步沟通 | 只使用事实库和版本化答案范围；未知、越界或敏感问题生成 Exception | 常规回复可推进，承诺类问题不越权 |
| F11 | 自动约面 | 本地时段锁、新鲜日历复查、候选人私有 tentative event、日历结果落盘、招聘确认、双操作幂等/对账与成功通知 | 只有回复和日历两侧均明确成功，Interview 才进入 `SCHEDULED`，Application 记录 `INTERVIEW_SCHEDULED` 里程碑 |
| F12 | 异常收件箱 | 告知原因、上下文、建议、截止时间和有限决策；支持一次处理或更新规则 | 处理后只恢复受影响流程 |
| F13 | 稳定态概览 | 以产品内 Inbox 展示 Autopilot 状态、最近完成、异常、外部通知状态和已约面试 | 首页不要求用户逐个审批岗位，且产品内事实不依赖邮件送达 |
| F14 | 活动与审计 | 展示动作、授权来源、证据、外部结果和失败原因 | 用户能回答“系统做了什么、为什么” |
| F15 | 面试移交 | 准备包含 `rawSnapshotStatus`：raw 可用时包含 JD 快照；raw 已到期清除时明确显示 `RAW_PURGED`，仅保留不可重建摘要、去敏来源/hash与重新导入确认入口；两种状态都包含匹配理由、实际投递材料版本、沟通时间线、联系人、确认时间/时区/地点/会议链接和日历状态 | 用户能区分“当时原始快照”“新导入副本”和“原文已清除”，不会被伪造的恢复误导；AI 面试建议不作为 P0 必需内容 |

## 8. 自动化等级体验

### 阶段 A：Dry-run

系统生成判断、材料和动作预览，但不执行。用户校准事实、硬条件和材料风格。

### 阶段 B：真实 L2 前的 Shadow

对每项将产生真实外发的 capability，系统必须先连续 7 天只生成、评估和对比“本应执行”的计划，真实外部副作用保持为 0。任何未解释的覆盖空窗、绑定变化或严重错误都会使该 capability 的 Shadow 失效并重新开始；用户确认不能跳过此门。

### 阶段 C：L2 校准

Shadow 通过后，外部动作才可进入逐次确认。系统记录真实 L2 动作、用户修改、拒绝和原因，逐步形成可委托规则。匹配、材料等不产生外发的 capability 可直接在人工复核中积累校准证据。

### 阶段 D：L3 就绪检查

系统展示透明清单：事实完整度、硬条件、连接器权限、白名单、限额、答案范围、日历窗口、通知、急停与回滚均通过。是否开启仍由用户明确决定。

### 阶段 E：按能力开启 L3

发现评分、材料、投递、跟进回复、自动约面分别授权。每次升级展示策略 diff、有效期、最大执行量与异常条件。

### 阶段 F：监控与回退

某项能力异常时只回退该能力到 L2；用户也可“暂停新机会”（`PAUSE_NEW`）、“停止全部外发”（`STOP_OUTBOUND`）、暂停某一 capability、撤销策略版本或全局急停（`KILL_SWITCH`）。

### 已接受的默认值与 L3 门槛

| 约束 | v0.1 基线 |
| --- | --- |
| 默认业务上限 | 每日投递 10、每小时回复 8、每日自动约面 3 |
| 普通配置硬上限 | 每日投递 25、每小时回复 12、每日自动约面 8 |
| 自动跟进 | 默认关闭；显式开启后每个 Application 最多一次 |
| 所有真实业务外发 | 包括 L2 逐次确认在内，对应 capability 首次业务外发前必须先完成连续 7 天 Shadow；Accepted ADR-0003 的固定 heartbeat、一次停止告警和删除期固定撤权仅走隔离安全控制面 |
| 匹配 / 材料 L3 | 每项至少 50 个校准决策 |
| 投递 / 回复 L3 | 每项至少 20 次真实 L2 动作 |
| 自动约面 L3 | 至少 5 次真实 L2 动作，并通过至少 20 个合成异常 Case |
| 零容忍门槛 | 未授权、重复、虚构、错误排期事件均为 0 |

L3 必须按 capability 独立开启、暂停和恢复。进入 `STOP_OUTBOUND` 或 Kill Switch 的同一事务，全部已登记外发 capability 都写入新的 `recoveryEpoch` 并置 `recoveryRequired=true`。解除后旧 ActionPlan 和旧授权不得复活；完成对账后，只有当前 connector/account/credential binding 与有效 Shadow receipt 均未变化的 capability 才由用户发布新授权、先恢复到 L2，并只清除该 capability 匹配的 recovery epoch；binding 或 criteria 变化则先回到新的 7 天 `PRE_L2_SHADOW`。即使 Workspace 回到 `RUNNING`，其他未清 recovery barrier 的 capability 仍失败关闭。备份恢复不还原凭证，重新绑定产生新 credential lineage，因此外发 capability 必须先完成新的 7 天 Shadow、取得新 receipt，随后才能恢复 L2；真实样本、健康检查和明确确认通过后才可重新进入 L3。

### 历史 Campaign 的只读动作矩阵

`LISTENING` 只用于收取并核对已经存在的申请事实，不是隐形的第二个活跃 Campaign：

| 动作 | `LISTENING` |
| --- | --- |
| 发现、导入或评分新岗位 | 禁止 |
| 为未投岗位生成新外发材料或 ActionPlan | 禁止 |
| 创建新 Application、投递或自动跟进 | 禁止 |
| 读取既有 Application 的迟到回复、面试变更和外部结果 | 允许 |
| 对既有 unknown Operation 做只读对账 | 允许 |
| 新回复、改期或取消所需的任何外发 | 禁止由该历史 Campaign 创建或授权；只展示事实并进入 Exception/人工交接。若用户要继续自动推进，必须在当前唯一活跃 Campaign 下显式接管并创建全新的 Plan/Authorization，不能复活历史授权 |

历史 `LISTENING` 可与一个新的 `CALIBRATING`/`ACTIVE` Campaign 并存，但 Workspace 全局去重和硬限额仍覆盖所有 Campaign。

## 9. 成功指标

### 北极星

**ABQI：每位活跃求职者每月由 RoleFox 在无需日常人工介入的情况下约到的合格面试数。**

合格面试必须通过用户硬条件、真实有效且未重复，时间已经双方确认并写入授权日历，用户愿意参加，且未依赖虚假信息或越权承诺。

为保证该指标可计算，v0.1 采用以下数据字典：

- **活跃用户月**：报告月内至少有一个 Campaign 处于 `ACTIVE`，且 RoleFox 在该 Campaign 下至少处理过一个有效岗位或既有 Application 的新外部事实；只有 `LISTENING` 的 Workspace 不计入活跃用户分母。
- **无需日常人工介入**：从该机会进入当前 Campaign 到 Interview=`SCHEDULED`，用户为推进常规流程执行的逐岗位筛选、材料编辑、逐次批准、催进度或人工约时次数必须为 `0`。首次配置、用户主动修改长期规则、真正的 Exception 决策和查看准备包不冒充日常动作，另行报告其次数与耗时。
- **愿意参加**：必须保存可审计证据——用户对该 Interview 的明确参加确认，或覆盖该岗位与精确时段的有效版本化求职/排期预授权；统计截止时已拒绝或取消的不计入。
- **聚合口径**：先计算每个活跃用户月的合格面试数，再报告均值、分布和零结果占比；不得用总面试数除以注册用户数替代。

### v0.1 领先指标与初始目标

这些是待验证目标，不是当前数据：

- 应用运行后，至少 4/5 首次测试者在 20 分钟内完成工作区、一个 Campaign 和首次 Dry-run，且所有测试者均在 30 分钟内完成；
- 高匹配推荐接受率 ≥ 70%；
- 80% 以上材料只需轻微修改，事实错误为 0；
- 校准后，常规步骤的 L3 覆盖率 ≥ 80%；
- 排除认证失效与平台挑战后，连接器动作成功率 ≥ 95%；
- 从完成配置到首个合格申请的时间持续下降；
- 每个合格面试所需的候选人主动操作分钟数持续下降。

### 发布护栏

- 未授权外发动作：0
- 重复投递：0
- 虚假事实陈述：0
- 投错硬条件岗位：0
- 错误时间或日历冲突的自动约面：0
- 凭证或个人数据泄漏：0
- 因系统主动规避平台限制造成的投诉或处罚：0

## 10. 关键产品假设

1. 用户在达到各 capability 的明确校准门槛后，愿意授权有限的真实外发动作。
2. 一份版本化策略可以覆盖至少 80% 的常规决策。
3. 硬过滤加可解释评分能使用户接受至少 70% 的高匹配推荐。
4. 基于事实证据的材料能在零虚构前提下达到 80% 轻微修改即可使用。
5. 至少存在一条长期可维护的真实只读来源和一条受控动作路径。
6. 邮箱与日历足以验证第一条投后闭环。
7. 早期用户能接受本地部署；首次配置至少 4/5 测试者在 20 分钟内完成，所有测试者均不超过 30 分钟。

验证方法和止损门槛见 [验证计划](validation-plan-v0.1.md)。

## 11. 明确不做

- 多 Campaign 并行调度；
- PostgreSQL、跨数据库迁移和第二套正式存储实现；
- 跨日历 Provider 账户聚合；
- 多用户、团队或职业教练协作；
- 多个真实招聘平台同时写入；
- 原生移动端和桌面端；
- 完整简历排版器、模板商城和插件市场；
- 长期行为训练的复杂个性化模型；
- 托管 SaaS、计费和订阅系统；
- 大而全的数据分析看板；
- 无边界 L4 或批量海投。

## 12. 开源与商业假设

开源核心必须提供完整的单用户、自托管闭环，包括数据、策略、审计、连接器 SDK、导入导出和至少一种可真实使用的开放通道。

未来可选托管服务销售的是常驻运行、升级备份、维护连接器、多设备同步和支持，而不是安全能力或用户数据。候选人的付费周期天然可能较短，因此 v0.1 只验证两类付款假设，不开发计费：

- 活跃求职者是否愿意为省时间和常驻运行按月付费；
- 职业教练或就业服务机构是否愿意为持续协作与维护按席位或服务量付费。

安全策略、完整导出和账号删除不能成为付费墙。

## 13. 已接受决策与仍需验证的实现选择

v0.1 的 19 项产品与目标设计决定已经接受，原始基线见 [ADR-0002](../adr/0002-v0.1-product-decision-baseline.md)；业务 Shadow 与隔离安全控制边界由 [ADR-0003](../adr/0003-shadow-safety-control-exceptions.md) 澄清，JD raw 清除后的准备包行为由 [ADR-0004](../adr/0004-jd-raw-retention-and-preparation-pack.md) 修订。三份 Accepted ADR 共同构成当前权威产品决策。

以下运行与治理要求是 PRD 级验收契约，不依赖读者另行推断 ADR：

| 主题 | v0.1 已接受基线 |
| --- | --- |
| 数据保留 | 按 Accepted ADR-0004：原始 JD 有 Campaign 引用时取所有引用 Campaign 最晚 `endedAt+90d`，任一引用仍活跃则不清除；无 Campaign 历史时用 `importedAt+90d`。到期必须删除 raw/快照/可重建副本，即使摘要缺失或无效也不得延期；不可重建 `structuredJdSummary`、去跟踪参数且无 PII/secret 的 source ref、raw content hash随结构化申请历史/材料版本/最小审计摘要保留 1 年；消息正文/附件结束 90 天后删除，滚动备份保留 30 天。准备包随后显示 `RAW_PURGED`。重新导入须用户确认并建立新 lineage；同 hash 仅标为新导入匹配副本，异 hash 标 `REIMPORTED_DIFFERENT_VERSION`，均不改写旧历史或重置原时钟；跨会话保留过期 raw 必须显式创建 `RetentionExtensionRecord(extendedUntil)`。用户可随时导出/删除；延长默认关闭，撤销后重新计算，禁止暗中续期 |
| 安装支持 | Docker Compose 正式支持 macOS、Windows、Linux；macOS 原生开发正式支持；Linux/Windows 原生运行时为 best effort |
| 离线检测 | Worker 每 60 秒 heartbeat，连续缺失两次即在 120 秒判离线；最后状态有待办且离线超过 10 分钟时，由独立外部 Watchdog 向预设渠道告警；恢复后展示覆盖空窗与回补结果 |
| 日历 L3 门槛 | Connector 必须同时支持查询/对账、幂等创建、更新/取消和稳定 external ID；少任一项只能停留在 L2 或人工交接 |
| 约面部分成功 | 日历成功而回复失败时，以新的已授权补偿 Operation 取消 tentative event；取消失败、结果未知或补偿未获当前授权时创建 `SEV-1` Exception、暂停约面并交给用户 |
| 通知严重度 | `SEV-0`/`SEV-1` 立即提醒，`SEV-2` 进入每日摘要，`SEV-3` 只写产品 Inbox/活动事实；与需求优先级 P0/P1/P2 分离 |
| Kill Switch | 停止全部业务外发；内部审计和产品 Inbox 继续写；只有隔离、预配置、固定模板且按 kill epoch 幂等的安全通道可发送一次停止告警 |
| 日历隐私 | 只创建候选人私有 tentative event，不添加招聘方 attendee、不触发日历邀请邮件；对外确认只能经过已授权 Reply Connector |
| 持久化范围 | v0.1 只正式支持 SQLite；PostgreSQL 和跨数据库迁移是未来范围，不构成交付或发布门 |
| 真实投后闭环发布门 | 必须连接真实邮箱与真实日历 Provider，完成邮件读取、受控 L2 回复、日历查询/对账、候选人私有 tentative event 与双方确认的端到端验收；Fake Inbox 和测试日历只能作为先行验证，不能替代该发布门 |

以下仍是需要研究或技术 spike 的**实现选择**，不再是开放的产品基线：

1. 国际化、邮箱中心通道中的首个合规真实只读岗位源具体选型；
2. 首个真实 L2 动作采用官方 API、表单预填还是深链接交接；
3. 默认跟进冷却期的具体时长；自动次数已经锁定为每个 Application 最多一次；
4. 邮件、日历和可选 Webhook 的具体 Provider 与认证方式。

任何实现选择都不能弱化 ADR-0002、ADR-0003 与 ADR-0004 的授权、故障恢复、数据保留和安全边界。若找不到合规稳定的写入路径，真实业务动作继续保持 L2 或人工交接。

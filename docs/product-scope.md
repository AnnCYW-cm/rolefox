# RoleFox 产品范围

## 一句话定位

RoleFox 的目标是成为候选人掌控的、本地默认、可自托管的自主求职智能体：用户一次性提供真实资料、求职目标和授权边界后，它持续完成岗位发现、筛选、材料定制、投递、跟进、初步沟通和面试排期，直到把合格面试交给用户。

v0.1 的具体产品与目标设计边界已经由 [ADR-0002](adr/0002-v0.1-product-decision-baseline.md)、[ADR-0003](adr/0003-shadow-safety-control-exceptions.md) 与 [ADR-0004](adr/0004-jd-raw-retention-and-preparation-pack.md) 接受；决策治理由 [ADR-0005](adr/0005-sole-maintainer-governance.md) 固定为单一维护者模式。

产品类别是 **candidate-side job search operating system（候选人侧求职操作系统）**，不是招聘方 ATS，也不是批量投递脚本。

## 产品承诺

> **设定目标，等面试通知。**

招聘平台承担供需连接，但候选人仍需付出大量注意力完成逐个浏览、判断、打招呼、改材料、查看回复和协调时间。RoleFox 的价值不是让这些操作快一点，而是把候选人的日常参与从流程中移除。

用户只应负责三件事：

1. **提供真实信息**：履历、作品、技能和可对外使用的事实证据。
2. **设定目标与委托边界**：岗位条件、排除规则、质量阈值、投递节奏、可自动回答的内容和日历空闲窗口。
3. **参加面试**：收到已确认的面试通知和准备材料后按时参会。

常规情况下，用户不再逐个筛岗位、改材料、点击投递、催进度或来回约时间。RoleFox 只在规则未覆盖、信息矛盾、授权过期或需要本人做决定时打扰用户。

这是一种 **Policy as Authorization（策略即授权）** 的产品模型：用户批准一套有版本、有范围、有期限、可随时撤销的委托策略，而不是机械地审批每一个低风险动作。

## 0 号用户与通用产品

项目从发起人的真实求职困难出发，这能提供连续、具体的验证场景。但个人经历只进入私有工作区，不进入公共默认值或核心代码。

通用性的验收标准是：

> 更换候选人、目标职位、国家、语言、币种、模型或招聘来源时，只需修改用户数据、求职计划或连接器，不需要修改核心领域代码。

公共仓库中的 fixture、截图和演示内容必须全部合成。任何真实简历、通信、Cookie、账号或联系人信息都不进入版本控制。

## 目标用户

### 第一阶段核心用户

- 正在积极求职、同时管理多个职位的知识工作者
- 愿意自托管，或能完成基本配置的技术友好型用户
- 重视申请质量、隐私和控制权，而非无差别海投的用户

### 后续可扩展用户

- 中高阶人才、转岗者、跨地区和远程求职者
- 需要多语言材料的国际求职者
- 在候选人授权下协作的职业教练或求职顾问

### 暂不服务

- 招聘方的候选人管理、筛选或群发系统
- 猎头获客和候选人数据交易
- 绕过验证码、访问控制或平台规则的自动化
- 无规则、无上限、无法审计的批量投递

## 核心对象

- **Workspace**：数据、策略、地区设置和集成的隔离边界。
- **CandidateProfile**：候选人的基本身份与可验证事实索引，不混入某次求职目标。
- **ProfileEvidence**：工作、教育、项目和技能声明的事实依据。
- **SearchCampaign**：一段可结束、只读监听、归档或复制为新实例的求职计划；每个 Workspace 最多一个 `CALIBRATING` 或 `ACTIVE`，历史实例可只读 `LISTENING`。暂停由独立控制覆盖层表达，不增加 `PAUSED` 生命周期状态。
- **JobPosting / JobScore**：标准化岗位与针对某一计划的可解释评分。
- **ActionPlan**：任何外部动作在执行前必须形成的计划契约，包含内容哈希、风险、证据和过期时间；持久化阶段必须保证它不可变。
- **AutomationPolicyRevision**：用户委托的自动化等级、白名单、适用范围与频率限制；不可被用户放宽的 SystemSafetyPolicy、Workspace OperationalControl、CapabilityOperationalControl 和 Kill Switch 与其正交组合。
- **SchedulePreauthorization**：用户授权的日历账户、时间窗口及版本，允许 L3 在无冲突、无歧义时自动约面。
- **AnswerPreauthorization（M5）**：有事实依据、允许自动回答的内容或区间；未实现前敏感问题一律升级人工。
- **ActionPlanStatus**：动作自身从草稿、待审批或已授权、执行到成功、失败或过期的生命周期，不与申请阶段混用。

## 核心工作流

```text
配置工作区与候选人事实
        ↓
创建 SearchCampaign
        ↓
发现 → 标准化 → 去重 → 硬过滤 → 可解释评分
        ↓
生成事实可追溯的定制材料
        ↓
ActionPlan → 策略判断 → 外发能力先完成 PRE_L2_SHADOW → L2 逐次批准 → 达门槛后限定 L3 / 异常时询问用户
        ↓
等待回复 → 按规则跟进 → 初步沟通 → 自动约面
        ↓
SCHEDULED → 立即通知用户并移交面试
```

去重先使用稳定的 connector + externalId 或规范 URL 指纹；跨来源只建立疑似重复组并由用户消歧，绝不在歧义时自动合并。每个 Workspace 对同一已确认机会最多一个活跃 Application。`CLOSED` 是带原因的终态；新外部事实或用户明确 reapply 时创建关联的新 Application，旧实例不倒退。

自动约面采用 calendar-first：本地锁定时段、复查同一 Provider 账户下所有 busy calendar、在唯一写入日历创建候选人私有 tentative event、落盘明确结果后再通过 Reply Connector 确认。事件不邀请招聘方；日历与回复均明确成功后 Interview 才进入 `SCHEDULED`，Application 只记录 `INTERVIEW_SCHEDULED` 里程碑。

## 产品原则

1. **本地默认，可自托管**：M1 从单用户本地部署开始；托管能力是未来可选项。
2. **配置属于用户，密钥属于部署环境**：用户偏好不塞进环境变量，凭证不进入数据库导出或仓库。
3. **证据优先**：材料生成只能引用事实库中的内容，并能追溯到 evidence ID。
4. **核心掌握风险**：连接器可以提出动作草稿，但 `ActionPlan`、风险策略和授权判断由核心系统拥有。
5. **安全失败**：不确定、冲突、敏感或过期的动作默认暂停，而不是猜测执行。
6. **接口可替换**：AI、存储、岗位来源、执行器和通知渠道都不能成为单一厂商锁定点。
7. **渐进建立信任**：新用户先用 Dry-run 校准规则；任何真实业务外发 capability 在首次 L2 前完成连续 7 天、零业务外发的 `PRE_L2_SHADOW`，取得与当前绑定一致的 receipt 后进入逐次确认 L2；样本与安全门进一步通过后才开启 L3，使面试前流程在委托边界内自动运行。Accepted ADR-0003 的固定 heartbeat、一次停止告警和删除期固定撤权仅走隔离安全控制面，不取得业务模式或 Grant。

## 非目标

- 保证用户获得面试或 Offer
- 自动捏造、夸大或改写候选人经历
- 在第一版覆盖所有国家、职业和招聘平台
- 把候选人数据出售给招聘方或用于广告定向
- 用隐藏排名或付费渠道改变岗位推荐结果

## 成功指标

第一阶段不以“投递数量”作为北极星指标，而关注：

**北极星指标：每位活跃求职者每月由 RoleFox 在无需日常人工介入的情况下约到的合格面试数。**

合格面试必须符合硬条件、真实有效、未重复，时间已经双方确认并写入日历，而且用户愿意参加。护栏指标包括：

- 每个合格面试消耗的候选人主动操作时间
- 日常人工介入率与异常原因
- 合格投递到有效回复、面试的转化率
- 生成材料的事实错误与用户修改幅度
- 未授权动作、重复投递、错误外发和虚假陈述次数（目标始终为 0）

## 产品边界决策

- 单用户先行，但领域模型保留 workspace 边界。
- 通用核心先行，但连接器按平台逐个交付和维护。
- Web + Worker + Local Runner 足够支撑前期，不提前拆微服务。
- 默认 L2 是建立信任的起点，L3 才是“面试前 Autopilot”的目标体验；无限制 L4 不开放。
- 开源版本必须保持单用户完整可用；未来托管服务只能提供便利性、运维和协作增值。
- 产品内 Inbox 是通知事实来源，邮件是默认外部通知，Webhook 为可选适配器。
- 旧 Plan 和授权在急停或恢复后不复活；若 connector/version/account/credential lineage、Shadow criteria 或 coverage epoch 发生变化，按 capability 先回到连续 7 天零外发的 `PRE_L2_SHADOW`，取得新 receipt 后才能创建新的 L2 授权；仅在绑定未变化且当前 receipt 仍有效的普通控制解除路径中，才可在完成对账后回到 L2。L3 始终还需健康检查、样本门和明确确认。
